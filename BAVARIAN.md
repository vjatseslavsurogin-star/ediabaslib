# Bavarian Diagnostics 0.4 — USB preview

Based on [Deep OBD / EdiabasLib](https://github.com/uholeschak/ediabaslib), Ulrich Holeschak, GPL-3.0. Original license and source remain in the repository.

This branch builds a debug APK with package ID `org.bavarian.diagnostics` (separate from the original app). The launcher shows a USB hardware check and ECU asset status. USB enumeration does not send diagnostic requests. A recognized VID/PID is not proof of a functioning K+DCAN cable or vehicle communication.

## Missing ECU data
Upstream `BmwDeepObd/ReadMe.txt` requires the matching encrypted ECU asset in `BmwDeepObd/Assets/Ecu.bin` (or its matching split asset set). The original code requires its presence and verifies the package; these checks have not been disabled. Obtain the matching package with authorization from the upstream project/data provider. Do not commit proprietary diagnostic data to this public fork, and do not bypass license, encryption or validation checks. A local build with authorized assets can use the same dotnet build settings as the workflow. The public CI artifact is only a hardware preview unless valid data is provided. Keep at least 3.4 GB of free storage for original ECU extraction.

## First test
1. Download the latest successful artifact from the branch Actions page. Extract the signed debug APK.
2. Install on an Android phone (Android 7+ according to the project, actual compatibility untested).
3. Connect the FTDI K+DCAN adapter via OTG. Refresh hardware check; record VID/PID.
4. Do not use any coding, actuator or firmware-writing features. The inherited diagnostic engine contains write-capable functions and is NOT yet a read-only restricted implementation.
5. Vehicle diagnostics are not verified; they require authorized ECU data and actual on-vehicle tests.

CI disables bundled PIC adapter updates for the USB baseline. No firmware placeholders are used. No connection or vehicle signals are simulated by the launcher.

## 0.5: local ECU library (offline)
Import legally obtained BMW EDIABAS .PRG and .GRP files from Android's system file picker. Files are copied into private storage, not uploaded. Existing names are not overwritten. Use a single matching ECU data release; do not mix variants. The inspector uses EdiabasNet with no hardware interface and NoInitForVJobs=true to enumerate _JOBS for individual PRG files, without executing any actual ECU job. Group identification is not executed. This is separate from the encrypted upstream asset: no checks are bypassed. Import is not a live diagnostic connection and no compatibility with an actual DDE is yet established. No proprietary ECU binaries are distributed. To obtain your own files, consult the authorized BMW Standard Tools installation's EDIABAS/ECU directory and confirm the DDE/EGS variant with a diagnostic tool. The debug build is not yet tested on Android hardware.

## 0.6: language settings
Bavarian launcher and ECU library have an independent persisted English/Russian UI setting (English default). The inherited diagnostic engine is configured for English; known preview errors use English and raw external exception text is not shown in the preview. Raw ECU job names, DTC identifiers and manufacturer-supplied descriptions are not translated by this feature. A verified English DTC mapping and live ECU testing are still required. System Android dialogs may use the device language.

## 0.7: private preloaded ECU library
A separately assembled personal APK can carry an authorized ZIP in assets/bavarian_ecu.zip. The launcher imports the approved filenames into private app storage without overwriting existing files, validating size and file header and staging each file. Public CI builds do not contain this ZIP. This feature does not replace the original encrypted Deep OBD package or enable live diagnostics, and is for authorized local data only. Private APK packaging must re-sign the modified APK; a different signing key may require uninstalling the previous debug build (which deletes app data). No actual ECU data is committed to this repository.

## 0.8: experimental USB vehicle diagnostics
Independent local PRG path, using EdInterfaceObd and EdFtdiInterface. Exactly one supported USB adapter must be attached; permission is requested separately. Manual DDE/EGS PRG selection, IDENT first, then FS_LESEN and specific read-only status commands. Approved PRG hashes are pinned to the personal E60 data set; arbitrary imported files cannot execute in this screen. No clear-fault, coding, adaptation, actuator, or flash actions. Raw ECU result keys and values are displayed as supplied, not translated or interpreted as verified DTC descriptions. Test with vehicle stationary, ignition on. A positive identification response is not yet a verified match of exact vehicle variant. Disconnect or leave the screen to reset identification. Vehicle test and signal scaling verification are still pending. Public APK contains no personal PRG files.

## 0.9: complete private E60 V74 library
The private APK seed is the user's normalized 675-file archive (259 PRG, 416 GRP), checked by SHA-256, flat filenames, count, size and basic header type. Existing conflicting files are preserved and reported. Initialization is off the Android UI thread. The public CI template contains no proprietary data. The local offline inspector supports the expanded library. Live execution stays restricted to the previously hash-pinned DDE/EGS PRGs and read-only job allowlist; the other files are not proof of vehicle compatibility and do not enable whole-car scans, coding or flashing. Actual vehicle communication is not yet verified.

## 1.0 Test Edition
Manual identification confirmation and repeated IDENT fingerprint before subsequent reads, USB presence polling and cancellation, local bounded test report (timestamps, PRG, job, raw returned fields, elapsed time, EDIABAS errors), explicit text sharing and deletion. Report may contain vehicle identifiers; no automatic upload. The report is job-level, not a byte-level bus trace. Full library verification required before opening vehicle screen. No new vehicle commands, automatic scan, write operations, or validated live charts. First test stationary with ignition on, engine stopped, then compare readings with a known diagnostic tool. The manual confirmation/fingerprint does not establish exact ECU compatibility on its own.

## 1.1 Auto identification
Separate engine and transmission entry points use the hash-pinned D_MOTOR.GRP and D_EGS.GRP with the native EdiabasNet ResolveSgbdFile mechanism. Resolved variants must match the family allowlist and their pinned PRG hashes before explicit IDENT or data jobs. Every read resolves again and compares the PRG and identification fingerprint. Last successful variant is stored locally for display only, not trusted as a current connection. Manual variant selection and confirmation remain in Developer mode. No fallback guessing, whole-car scan, coding, or flashing. Group job names and files checked offline; actual group behavior and vehicle communication remain untested. Public build contains no ECU data.

## 1.2 Live Data (experimental)
Live polling enabled only on the two variants demonstrated in the first vehicle reports (d50m57e0 and gs19a). One transport session, sequential jobs, verified identification at session start, 200 ms delay between cycles, 10 minute maximum, stops on cancellation, USB loss, invalid numeric data/unit or communication error. CSV is long format, one UTC-timestamped row per reading, with source, variant, raw parameter name, numeric value, unit and elapsed job time. Export via Android document picker; latest file per system, no network upload. Charts display actual versus target in native ECU units, with 60-cycle history. Experimental additional read-only jobs are limited to those present in the two inspected PRGs; semantics, arguments and readings are not yet vehicle validated. German fault detail preserved, status labels mapped only for observed codes 32/33/35, other values remain unknown. DEMO source explicitly marked and never opens USB. No fault clearing, flash, coding or other writes. V1.1 vehicle reports confirmed the basic DDE/EGS queries, not continuous polling or V1.2 behavior.

## 1.2.1 Dedicated DTC screen
Home Fault codes opens a sequential DDE/EGS scan using the existing hash-pinned group resolution and IDENT + FS_LESEN allowlist. Each module has an independent success/failure result; unrecognized status stays unknown. Status 32 hidden by default, show all to inspect. Seven short English/Russian labels are scoped to the two tested PRG variants and the observed records. Original ECU details remain accessible. Warning capability is not actual MIL state. No clear-fault command or writes. No full vehicle scan. New interface and combined scan not yet vehicle tested.

## 1.5 Vehicle scan (experimental)

## 1.6 Service & history
Local history up to 50 scan/MIL/clear reports, including incomplete scan results, share on demand. Experimental OBD Mode 01 PID 01 via hash-pinned obd.prg, exact MIL result name, unknown if unrecognized; does not infer lamp from DTC. Explicitly confirmed per-ECU fault clear only for d50m57e0.prg and gs19a.prg, following current scan, identity recheck, local pre-clear snapshot, ECU acknowledgement and memory reread. DDE clear all argument 0xFFFF, EGS no argument per PRG descriptions. Does not perform readiness manipulation, coding, adaptation reset, flash, or clearing other modules. Engine must be off and car parked; operator must verify. New commands not yet tested on vehicle. Private release signing key must be reused; never commit key or proprietary ECU archive.
